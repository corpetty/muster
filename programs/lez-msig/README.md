# lez-msig

An M-of-N multisig program for the Logos Execution Zone, private by default, on LEZ v0.3 and
v0.4. Built for RFP-005. The accepted proposal is the reference for scope and milestones
(`docs/proposals/RFP-005-lez-msig.md`, logos-co/rfp#299), and progress against it is
`docs/proposals/RFP-005-roadmap.md`.

- **The program** enforces the quorum itself. Members' BIP-340 approvals are verified inside its
  execution, with roles, expiry, a time lock, spending limits and weighted approvals.
- **One program, two postures.** It runs over a public PDA (the public posture) or a group-owned
  private PDA (the private posture: on chain, one proof with no member, approval or config in
  it).
- **No coordination layer is required.** The program does not care how approvals were
  collected. Muster's encrypted room is one way; your own transport is another.

Design and decision log: `docs/design/lez-msig.md`. What a signer signs, byte for byte:
`docs/design/lez-msig-signing.md`. Benchmarks (real proving): `BENCHMARKS.md`.
What each observer sees for each action, the cross-layer correlations, and which test holds each
RFP requirement: [`docs/design/lez-msig-guarantees.md`](../../docs/design/lez-msig-guarantees.md).

## Layout

| Path | What it is |
|---|---|
| `core/` | `msig_core`: the rules as pure functions, with no LEZ dependency. Every rule is tested here. |
| `v03/` | LEZ v0.3 wire types and the account derivation, shared by the guest and the host |
| `methods/` | the guest, and the deployed build in `artifacts/msig.bin` (its image id is the program's identity) |
| `host/` | `msig_host`: the client (`public.rs`, `exec.rs`), the `msig_exec` CLI, the benchmark and the vectors |
| `module/` | `lez_msig_module` (0.1.x): the same operations as a Logos module (`lez_msig_module.lidl`) |
| `lez04/` | the LEZ v0.4 line, its own cargo workspace over the same `msig_core`: the actor adapter (`v04/`), the deployed guest, `msig_host04` (client, `msig_exec04`, tests) and `lez_msig_v04_module` (0.2.x). See `lez04/CLAUDE.md`. |

## IDL

`lez04/idl/lez_msig.json` is the program's IDL (version 2), generated by SPEL (`logos-co/spel`,
branch `refactor/lez-v0.4.x`, pinned in `lez04/tools/idl.sh`) from `msig_core` itself. The types are
named in `lez04/spel.toml`, never marked in the source, so `msig_core` keeps no LEZ or SPEL
dependency:

```
cd lez04 && tools/idl.sh           # regenerate (installs the pinned spel once; SPEL=<binary> to use your own)
cd lez04 && tools/idl.sh --check   # the committed IDL is what spel generates, and decodes Muster's State vector
```

CI runs the check (`lez-msig-idl` in `.github/workflows/lez-e2e.yml`).

- `messages` is `msig_core::Instruction` (Create, Execute, Queue, ExecuteQueued, Spend), and
  `state_types` is `msig_core::State`. SPEL describes every type they reach: enums with struct
  and tuple variants, `u128`, `Option`, nested `Vec`s, `[u8; 32]` keys and `[u8; 64]` signatures.
  `spel inspect --idl lez04/idl/lez_msig.json` decodes a multisig's state.
- What the v0.4 guest decodes is `msig_v04::ProgramInstruction`, the struct
  `create_key ‖ placement ‖ Instruction`. An IDL v2 message is an enum whose tag is the first
  byte, so SPEL refuses the struct (`ProgramInstruction is not an enum`). The `Placement` enum is
  not describable either: its private variant holds LEE's `NullifierPublicKey` and
  `ViewingPublicKey`, which are not in `msig_v04`'s path dependencies. So the instruction's bytes
  follow 33 bytes (create key and `Placement::Public`) on the public posture, and the IDL alone
  cannot build a lez-msig message: `spel send` does not work for it.
- SPEL's encoder (`spel encode`, a fault of the CLI, not of the IDL) mishandles a `Vec` inside a
  JSON-valued field, held against Muster's vectors (`module/tests/vectors/lez-msig/vectors.json`,
  2026-11-26, spel `0d42ddb9`):
  - it refuses `Config.targets` and `SpendingLimit.signers` (`Vec<[u8; 32]>`, even empty),
    `Action::Call`'s `rows` (`Vec<Row>`) and `Action::Config` (`Vec<ConfigChange>`);
  - it encodes `Action::Cancel([3, 300])` as `Cancel([3])`, silently;
  - an `ExecuteQueued` of a transfer it encodes byte for byte as the vector.

## Use it without Muster (public posture)

On the v0.3 line today. The v0.4 executor carries the private posture's operations only. Making
both lines usable this way is the accepted proposal's M2 (exo-dbd3).

Every operation is one JSON request and one JSON answer, with no key involved. They are
available from three places, which share one implementation (`msig_host::exec::exec_request`):

- the CLI, `msig_exec` (`cargo run --release -p msig_host --bin msig_exec`), which reads the
  request on stdin;
- the Logos module `lez_msig_module`, one method per mode, callable from any module or from
  `logoscore -c`;
- the Rust library, `msig_host::public`.

The journey, with `R='"rpc":"http://127.0.0.1:3040","program":"<id>","createKey":"<32 random bytes>"'`:

1. **Create.** Send `{"mode":"prepare",R,"kind":"create","zone":<32 bytes>,"config":{"members":[{"key","roles":7,"weight":1},…],"threshold":2},"payerKey":<your x-only key>}`.
   The answer is `{sign, message}`. Sign `sign` with the payer's key (BIP-340), then send
   `{"mode":"send_public","rpc":…,"message":…,"witnesses":[{"signature","publicKey"}]}`.
2. **Read.** `{"mode":"state",R}` returns the config, epoch, free nonces, vault balance and
   queue.
3. **Propose.** `{"mode":"propose",R,"action":{"kind":"transfer","to","amount"},"proposer":<a member's key>,"expiresMs"}`
   returns `{proposal, approveMsg, …}`. Show each signer the decoded action, then have them sign
   `approveMsg`. The proposer signs too.
4. **Check.** `{"mode":"check",R,"kind":"execute","proposal":…,"approvals":[{"key","sig"},…]}`
   returns the program's own verdict against the state now: `{ok:true}`, or `{ok:false, refusal}`
   with a stable code such as `below-threshold` or `stale-epoch`.
5. **Execute.** `prepare` with the same instruction plus `payerKey`, then `send_public`, as in
   step 1. Use `kind: "queue"` (then `"execute-queued"` after the ETA) when the multisig has a
   time lock.
6. **Judge by the state.** On v0.3 a refused transaction is still included. Read `state` again:
   the nonce is spent, or the action is queued.

Spends under a spending limit follow the same shape: `spend` returns `{spend, spendMsg, period,
periodMs}`, the limit's signers sign `spendMsg`, and you `check`, `prepare` and send with
`kind: "spend"`. Config changes are proposals with `action.kind = "config"`; see the module
contract for each change's fields.

The payer gains no authority: the approvals inside the instruction are the program's only gate.
`live_public.rs` runs this whole journey against a real sequencer.

## The private posture

A private multisig's transactions are proved on the member's machine (minutes per transaction,
see `BENCHMARKS.md`). Proving needs the group's secret, which only members hold. `exec`, `fund`,
`scan` and `send` in `msig_exec` and the module do it, and the module holds no key: the secret
arrives with each request and is dropped with its job. Muster carries the secret and each new
note between members in its encrypted room (`docs/design/lez-msig.md` §8).

On v0.4 (`msig_exec04`, `lez_msig_v04_module`):
- Every private transaction pays its fee inside its proof, from a fee account the group's secret
  derives (D17). `topup` funds that account from a member's public account. Each request carries
  the fee account's note and answers with its new one.
- The program is proved undisclosed (D18), so a transaction names no program.
- `recipients` seals a payment to a private payee, which only that payee can open and claim.
- Anyone can pay the vault's address from a public account. `inbound` lists those deposits, and
  `collectFrom` collects them in the next transaction.

## Status

Built for LEZ v0.3 and v0.4, and released with Muster since muster-v0.4.0, which ships both
provers. Both postures run on the LEZ 0.4.0-rc3 devnet with real proving.
