# Muster — Implementation Plan

Companion to `01-furps.md`. Requirement IDs (F-x, FS-x, U-x, R-x, P-x, S-x) refer to that document. Phases are ordered so that every phase ends with something runnable and tested, and the UI arrives only after the protocol core is proven headless.

Target platform: **logos-core**. The backend is a Nim core behind a published LIDL contract, wrapped as a module and packaged as `.lgx`; the frontend is a QML module rendered inside **logos-basecamp** (and launchable standalone, following the pattern of the other platform UIs). Headless phases run on the **`logoscore`** CLI runtime. This is the same shape as the existing Storage and Chat modules — both are non-C++ engines behind a generated module surface — so distribution, loading, capability policy, and packaging are platform problems already solved.

## What we build on, and what we only read

Two different things got conflated in the first draft of this plan: the runtime the platform *ships*, and the runtime the specs *describe*. They are not the same runtime, and Muster targets the first.

### The contract layer: LIDL

`logos-co/logos-lidl` is the platform's **language-neutral module contract**: a lexer, parser, AST, serializer and validator for the Logos Interface Definition Language, in dependency-free standard C++. A `.lidl` artifact declares one module's callable surface — metadata, `depends`, record types, `method`s with parameters and return types, and fire-and-forget `event`s. Each SDK supplies a codegen backend over that shared frontend, so a module can be called from any other language without building, linking, or sharing source with it.

**Muster is contract-first: `muster.lidl` is the module's public surface**, and the Nim core sits behind what it generates. This replaces the hand-written bespoke C API the previous draft of this plan assumed — a bespoke header would have been a private convention where the platform already has a published one.

Two properties make this land well for us:

- **Its type vocabulary is CDDL's** — `tstr`, `bstr`, `int`, `uint`, `float64`, `bool`, `any`, `?` for optional, `;` comments — plus `result` (structured success/value/error), which CDDL lacks. The spec's own "Why not just use CDDL?" section is the cleanest statement of the split we arrived at independently: *CDDL describes data, not interfaces*. It has no notion of a method, an event, or a module. So CDDL-family types describe our log, LIDL describes our API, and they are complementary rather than competing.
- **Wire serialization is explicitly out of LIDL's scope.** It says nothing about encoding, which means ADR-009 is untouched by adopting it: our deterministic signing-path encoding remains entirely ours.

Also worth designing around: `logos-rust-sdk`'s cross-language doctest shows a consumer binding an **interface dependency** — coding against a contract's *shape*, then binding it to a concrete provider at runtime (`GreeterClient::bind("cpp_greeter_module")`) with no build-time coupling. That is a better shape than a hard dependency for both ADR-006 and ADR-010: Muster codes against a delivery contract and a chat contract, and which module satisfies them stays a runtime decision.

### The Nim gap, and what fills it

There is no Nim SDK. The frontend is done and the bridge exists: `include/lidl/lidl_c.h` exposes `lidl_parse_to_json`, `lidl_serialize_from_json`, `lidl_validate_json`, and `lidl_free_string` — four C functions exchanging the AST as JSON, expressly so non-C++ SDKs reach the canonical parser without reimplementing the grammar. `logos-rust-sdk/lidl-gen/src/lidl_ffi.rs` binds it in ~106 lines; the remaining ~3.2k is Rust-specific emission.

So the work is a Nim backend, not a parser. Two cautions the C header states outright: strings are malloc'd and must be freed with `lidl_free_string`, and optionality must be read from the derived `isOptional` / `valueType` keys — never from the raw `optional` / `type` spelling, which exists only so the wire form round-trips.

For the Nim-behind-FFI half, `logos-storage/logos-storage-nim` → `logos-storage-module` is the worked example: a Nim engine behind a C API (`library/libstorage.h`, `libstorage.nim`, `ffi_types.nim`, `alloc.nim`, thread-request plumbing) with generated module glue. Copy from it:

- **The external-lib build path** — `mkExternalLib` + `logos-module-builder`, driven by one `metadata.json`.
- **The contract-is-the-API discipline** — storage's `CLAUDE.md` insists method signatures, `metadata.json` events, and emitted event strings stay in sync. Contract-first makes this structural rather than a rule to remember: `muster.lidl` is the single source, everything else is generated from it.
- **Async-over-FFI** — storage's split between fire-and-forget event-emitting callbacks and blocking sync getters, including the `abandoned` flag that prevents use-after-free when a caller times out. We need exactly this seam between chronos and the host thread.

### logos-core-poc2: reference, not skeleton

`logos-core-poc2` implements the *draft* module specs. It is a useful Nim reading of them, and its dependency lockfile is our pinned set (verified verbatim). But its exported symbol set and CBOR dispatch target the spec runtime, **not** the host basecamp loads today — so lifting `shell.nim` verbatim would produce a module the platform cannot run. Read it for:

- **Project mechanics**: `nimble setup -l` with local `nimbledeps/`, `nimble.lock`, `config.nims`, unittest2. Take these directly.
- **`runtime_cli loop`**: still useful as a throwaway two-instance harness if it saves time, but ADR-008 no longer makes it the P0–P3 dev host.
- **What not to inherit**: `schemas.nim` is a line-based CDDL extractor (`splitLines`, `line.contains("=")`) the authors treat as provisional. `cbor_stuff.nim:14` marks canonicalization as future work — "P1/P2: Full canonicalization (sorted keys, shortest integers, no tags)". Deterministic encoding is ours to build either way.
- Its tests were generated from the implementation to track behavior, not to encode intent — never copy them as spec.

### The draft specs: tracked, not targeted

The LOGOS-MODULE-* specs and cdCDDLe live on `logos-lips` branch `draft/logos-core-module-specs` (`docs/logos-core/spec-{module-interface,module-transport,module-runtime,module-commitment-model,module-hash-profile,cdcddle}.md`). Actively worked through mid-2026, still unmerged. We read them for design, and we adopt the parts that cost little and pay off immediately — deterministic encoding rules, domain-separated hash inputs. We do not adopt schema roots or verified views until they ratify (ADR-009).

The one thing worth watching: the commitment model's **verified views** — Merkle inclusion/absence proofs at typed semantic paths — are the natural fact-card proof channel for F-10. Until they ratify, F-10's `verified-locally` grade must be earned some other way (P5 note).


## Repository layout

One repo, two `.lgx` outputs. Split into module/ui repos later only if the platform's conventions demand it.

```
muster/
  CLAUDE.md                    # invariants + commands (repo root)
  flake.nix                    # builds module, ui, tests; dev shell
  docs/
    00-vision.md
    01-furps.md
    02-implementation-plan.md
    adr/                       # one file per decision gate below
  module/                      # Nim backend → muster-module.lgx
    src/
      api/                     # muster.lidl (normative contract) + generated surface — the only outward seam
      schemas/                 # CDDL sources + generated Nim types + golden vectors
      dcbor/                   # deterministic CBOR encode/decode
      crypto/                  # keys, sign/verify, envelope + epochs
      log/                     # hash-linked signed log, causal order, reducers, persistence
      intents/                 # effect types, lifecycle reducer, expiry
      drivers/                 # interface, conformance suite, stub, safe
      transport/               # interface, local/memory, messaging impl (ADR-006)
      plugins/                 # runtime, manifest enforcement, first-party
    tests/
  ui/                          # QML → muster-ui.lgx
    qml/                       # theme singleton (prototype tokens), components, home, composer, room
    tests/                     # logos-qt-mcp scripts (the six-step legend, U-1..U-9)
  infra/
    anvil/                     # Safe 1.4.1 deployment fixtures
```

### P0 — Module scaffold and the log

**Status: ✅ done (2026-08-19).** Loading spike passed (Nim-native module loads + dispatches in `logoscore`, Route B — a `codegen.nim` path added to `logos-module-builder`, PR #202 open upstream). dCBOR CDE encoder, domain-separated hash-input records, and the signed hash-linked log all landed with probes green (`exo-d7c`/`449`/`548`). No CDDL parser / cdCDDLe, per ADR-009.

**Step zero is a loading spike, before any Muster code.** Write a two-method `muster.lidl`, generate its Nim surface over the `lidl_c.h` JSON bridge, and get the resulting module loading and answering one call in `logoscore`. Everything downstream rests on this working; the storage-nim and rust-sdk precedents say it does, but we confirm it in days rather than discovering it at P4. The spike deliberately exercises the part with no precedent — the Nim backend — not the part with two. If the backend stalls, hand-write the generated surface for this one contract and keep going (ADR-008 fallback); either way `muster.lidl` stays normative and we know which world we are in before P0 proper.

Then: Nimble project with poc2's pinned dependency set. The §4.5 deterministic CBOR profile implemented over nim-cbor-serialization, with golden vectors that specifically catch the CDE-vs-RFC-8949 map-ordering trap (bytewise-lex of encoded keys, never length-first). Domain-separated structured `hash-input` records with our own domain tags (`muster.event.*`) everywhere we hash or sign — never ad-hoc concatenation. Schema identity per ADR-009: hand-assigned stable ids in a versioned `profile` + `schema-id` field, no CDDL parser and no cdCDDLe. Signed hash-linked log: append, ingest-verify (FS-2), causal ordering with deterministic tiebreak, reducer framework (R-3), all on chronos.

**Accept:** the module loads, dispatches, and unloads cleanly in `logoscore`. dCBOR golden vectors pass, including the map-ordering trap. Re-encoding any signed payload reproduces its bytes exactly, and every hash in the log is a domain-separated `hash-input` record — a test asserts no signing path uses raw concatenation. Two in-memory logs exchanging events in adversarial orders (shuffled, duplicated, interleaved) converge to byte-identical reduced state as a generated-input property test. A tampered event and a non-member event are rejected with distinct errors.

### P3 — Real transport and encryption

**Status: 🚧 core complete 2026-08-21; hosted surface + live-node test remain.** ADR-010 resolved then **amended** (persistent, room-scoped identity — FS-7 reframed; the platform mixnet closes FS-9): build a thin ECIES stopgap behind a `ConversationCrypto` interface, native `logos-chat-module` the target once it ships persistence + removal. **Built + tested against `LocalTransport`** (`module/src/transport`, `crypto`, `coordination`; commits `7dea6a8`…`2a1f0ad`): the `lp_*` C-ABI Nim binding + `DeliveryTransport`; secp256k1 ECDH (reusing the Safe key) + ECIES-secp256k1 `EpochCrypto` with **F-16 verified** (a mid-conversation joiner cannot open earlier epochs, a removed member cannot open later ones); the multi-instance coordination flow (two instances converge, outsider blind, late member catches up); the foreign-thread GC seam (delivery callback enqueues, `poll()` drains on the module thread) + async send; and the payoff — **the intent lifecycle as `reduce(log)`**, so two owners coordinate a real Safe intent over encrypted transport and converge on it reaching `executable` (a non-owner signature never counts). The full P3 stack links in the shipping plugin (secp256k1 + libsodium). **Persistent identity (FS-4) landed 2026-08-23** (`3721514`, `2ba0bb8`): a `Keystore` *operation* seam (`address`/`pubKey`/`sign`/`ecdh`, never a key getter — a Keycard never releases its key, so operations are the only shape a real backend slots behind), a `FileKeystore` stopgap (secp256k1 secret minted on first open, persisted as an Argon2id-encrypted keyfile via libsodium `crypto_pwhash`+`secretbox`), and an `InMemoryKeystore`. The epoch layer routes its ECDH through the seam, so the secret never enters the coordination layer (`keystore_test` 6/6; the F-16 + convergence tests stay green through the refactor). The `identity()` lidl method is wired — the module opens its keystore under the host-provided instance path and returns `{address, pubkey}`; the portable `.lgx` builds clean with it in the regenerated surface. **Hosted coordination surface landed 2026-08-23**: `coordinate_join`/`coordinate_propose`/`coordinate_contribute`/`coordinate_intents` drive a conversation from a host over `CoordinationSession` + `reduceIntents` (multi-party `state = reduce(log)`), with content-addressed intent ids so hosts agree without a round-trip and owner recovery/verification done before publish (mirroring `approve`). This compiles `coordination/intents.nim` into the plugin (the `musterP3LinkCheck` stub is retired). Verified in-process (`tests/coordination_surface_test.nim`: two owners converge on a real Safe intent reaching `executable`, a non-owner is refused, a duplicate owner sig folds once) and the portable `.lgx` builds clean with the full surface. **Membership/grant handshake landed 2026-08-23**: a join-request/admit protocol over the coordination session (`coordinate_request_join`/`coordinate_pending`/`coordinate_admit`) — a joiner announces its key (no authority; admission is an existing member's explicit act, the core never auto-admits), and the new epoch key travels as an opaque ECIES control frame on the same topic (a 1-byte kind tag separates data / join-request / control). Admission re-keys forward so **F-16 holds over the wire** (the admitted member reads from its epoch on, nothing before its seam — `tests/membership_handshake_test.nim`). The mechanism sits behind the `ConversationCrypto` seam (`identity`/`admit`/`ingestControl`), so native chat's MLS commit/welcome replaces the ECIES grants as a binding change. **Remaining:** the live two-instance test over a real delivery node — the last piece, and the one that genuinely needs infra (a running Waku-backed node + two hosts). Original phase intent below.

ADR-006 is resolved: consume `logos-delivery-module` as a module dependency under the capability policy, behind our Transport interface. It wraps `liblogosdelivery`, and its API covers what F-15 needs — content topics, publish with delivery/propagation events, subscribe, store queries, and channels. The Transport interface stays, so embedding nwaku remains reachable if the module's guarantees turn out thinner than advertised.

- **ADR-008 Module shape and dev host** — resolved, replacing the earlier `runtime_cli` decision. Muster is **contract-first**: `muster.lidl` is the module's public surface, the Nim core sits behind what it generates, and the module is built via `mkExternalLib` + logos-module-builder. The dev host is `logoscore` from P0, not poc2's `runtime_cli`. Rationale: the LOGOS-MODULE-* specs are unmerged draft and a spec-native module does not load in the host basecamp uses, so "build to the spec and both hosts are reachable" was false; meanwhile LIDL is the contract layer that actually ships, and it is deliberately language-neutral. Cost: there is no Nim SDK, so we write a codegen backend over `lidl_c.h`'s JSON bridge (`logos-rust-sdk/lidl-gen` is the worked example — ~106 lines of FFI, the rest language-specific emission). We take that cost because the alternative is a private convention where the platform has a published one, and because the backend is a clean contribution back. Fallback if the backend stalls: hand-write the generated surface for our own contract, keeping `muster.lidl` normative. Validated by the P0 loading spike.
- **ADR-009 Encoding and schema identity** — resolved. Split the encoding requirement in two. *Determinism and domain separation* (same bytes in, same bytes out; every hash a domain-separated `hash-input` record) is a hard invariant from P0 — cheap now, and retrofitting it later would invalidate every signature already made. *Which profile derives schema identity* is versioned and swappable: v0 uses hand-assigned stable ids carried in a `profile` + `schema-id` field committed inside every signing payload, and cdCDDLe schema roots slot into that field later without a format migration. Rationale: nothing in the platform requires deterministic encoding — `logos-protocol`'s CBOR is non-canonical and interchangeable with JSON per-connection — so conformance to the draft profile buys future portability, not present correctness, while implementing a draft spec on a signing path risks both rework *and* a corpus of signatures under a superseded profile. Re-evaluate when the specs ratify, or the first time a second module must parse Muster events.
- **ADR-010 Chat module build-vs-consume** — **resolved (P3 start, 2026-08-21): BUILD Muster's own epoch layer for F-16; consume only `logos-delivery-module` (ADR-006).** A code-level investigation of `logos-chat-module` v0.2.2 and its crypto core `logos-messaging/libchat` (pinned `5c55c2ee`, 2026-07-26) settled all four deciding questions against consuming the chat/account layer. Three facts drive it: **(1) curve + binding gap** — chat identity is Ed25519/X25519 (`libchat/core/account/src/account.rs`, `directory.rs`; secp256k1/k256 appear only as transitive `alloy` deps, never in the identity path), with no authenticated binding to Muster's secp256k1 Safe key, so F-9's membership intersection needs a binding we'd have to design and test anyway; **(2) FS-7 is structurally violated** — group messages are DeMLS (openmls) and every MLS leaf credential binds a stable identity + Ed25519 verifying key to every message and commit (`core/conversations/src/inbox_v2/identity.rs`), and the module surfaces the directory-verified sender on every `message_received` (`chat_module.lidl`) — there is no unlinkable mode, so an anonymous driver is deanonymized at the chat layer; **(3) F-16 is unverifiable-and-partial upstream** — joiner forward-secrecy is inherited-and-*trusted* from MLS but has **no libchat test** proving the negative, and **member removal is not implemented at all** (no `remove_member` in `core/conversations/src`, none in `chat_module.lidl`), so the removal half of F-16 is absent; Muster would still have to author the "added member cannot decrypt earlier epochs" test itself, against a black-box stack it can only trust — contradicting the "verify rather than trust" bar. Reinforcing: the chat module is **ephemeral by construction** (`rust-lib/src/module.rs` `PERSISTENCE_ENABLED = false`; openmls on `MemoryStorage`), so it cannot survive the restart R-4/R-6 require. The upside of consuming (not writing crypto) is largely cancelled by the binding + anonymity + persistence + test-authoring work it would still demand. So F-16 is ours (ADR-002 default below), and `logos-delivery-module` — whose API confirms ADR-006 (content topics, publish, subscribe, `storeQuery`, reliable channels; it embeds its own Waku node) — is the only consumed dependency.

  **Amended (2026-08-21) — the identity model refined the posture from "build ours" to "build a labeled stopgap; native chat is the target."** The operator clarified the identity requirement (see FS-7 as reframed): identity is **persistent and known within a room**, encrypted from outside it — not individual anonymity. That **retires blocker (2)**: MLS binding a stable identity to every message is no longer a violation but the desired property, since that identity lives inside the encrypted group, not on the wire. The remaining reasons against consuming chat are now **completeness, not architecture** — member removal (unimplemented), persistence (`PERSISTENCE_ENABLED = false`, now a firm requirement since named identity must survive restart), and an untested joiner-forward-secrecy property — all of which improve as the module matures. Blocker (1), the curve, becomes a **per-member secp↔Ed25519 binding** (a member proves Safe-ownership by signing a link statement inside the room), not a reason to avoid chat. So the standing decision is: **build our epoch layer behind a `ConversationCrypto` interface as an explicit *stopgap*, with native `logos-chat-module` as the default target once it ships persistence + removal** — re-evaluated against upstream HEAD each phase. The lean-on-native posture also covers transport-metadata privacy: the Logos stack's coming **general mixnet** closes FS-9's linkability limit, and Muster routes through it when ready rather than building its own. Our ECIES-secp256k1 stopgap is deliberately thin and interface-isolated so the swap is a binding change, not a rewrite.

  **Amended again (2026-08-23) — F-14 relaxed from one curve to two bound identities.** A revisit re-validated ADR-010 against upstream HEAD (chat-module `a05d5119`, libchat `74265e6e`): upstream has **not moved on any deciding axis** — member removal still absent, `PERSISTENCE_ENABLED` still `false`, `message_received` still surfaces the directory-verified sender, account identity still Ed25519 — while Muster's stopgap now has all of removal, persistence, and a verified F-16. The revisit then re-examined the **one-curve constraint** specifically and found the framing "F-14's ideal, met" concealed a **key-reuse** problem: the identical secp256k1 secret was fed to both ECDSA (`signRecoverable`, Safe) and static ECDH (`ecdh`, epoch encryption), violating key separation. Decision: **relax F-14 to two bound keypairs** (the secp256k1 authorization identity + an Ed25519/X25519 encryption identity, joined by a signed link statement the core verifies on ingest — see F-14 as reworded). This fixes key separation in our own layer *and* builds exactly the secp↔encryption binding that consuming native chat needs, so the curve gap becomes a bridge. The build-vs-consume posture is unchanged (our epoch layer remains the stopgap; native chat the target); what changed is that the binding ADR-010 originally demanded ("either F-14 changes, or the binding is designed and tested") is now being built rather than sidestepped by one-curve. Supersedes the "one curve, no second identity" rationale recorded in the prior amendment and the mech-two-identities figure.

  *(Superseded framing, kept for the trail:)*

  **The curve conflict is the blocking issue, and it is confirmed at `logos-messaging/libchat` HEAD (2026-08-04).** `core/account/src/account.rs` holds `Ed25519SigningKey`/`Ed25519VerifyingKey` and derives `address()` as `hex::encode(verifying_key)`; `core/account/src/directory.rs` states it outright — "An Account (AccountAddress, an Ed25519 key) endorses a set of device keys." `core/crypto` is X25519 for DH and XEdDSA/Ed25519 for signatures. `secp256k1`/`k256` appear in the lockfile only as transitive `alloy` dependencies of `core/conversations`, never in the identity path.

  So libchat and F-14 hold the *same principle* — one curve serving both identity and encryption — on **different curves**. Consuming the chat/account layer therefore gives Muster two identities: a Curve25519 chat identity and the secp256k1 key that signs transactions. F-9 derives per-member role by intersecting chat membership with account membership, and that intersection needs an authenticated binding between the two keys which libchat does not provide. Resolve this before P3 writes any code: either F-14 changes, or the binding is designed and tested, or we build our own epoch layer and consume delivery only. Do not defer it into implementation.

- **ADR-012 Claims registry** — resolved: walkthrough claims are structured data checked in CI, not prose in QML. The vision's honesty rules and FS-9 are the only requirements whose failure mode is *copy* — nothing breaks when a caveat quietly disappears, which is exactly how honest documentation rots. So each claim is a record: the lifecycle step, the claim text, a `kind` (`protects` | `others-leak` | `gap`), and evidence. - **ADR-013 UI build chain — decouple `muster-ui` from the module's Nim-cdylib builder** — **validated end-to-end (P4 unblock, 2026-08-21, `exo-193`).** The working path to a rendering, real-engine UI **now**, while `exo-c6a`'s upstream fix lands on its own clock. Reversible: when the upstream codegen bump ships, re-evaluate returning to the single-builder chain.

  **VALIDATED:** `muster-ui` built on basecamp's coherent builder (`4717b9af`), baked into a `logos-basecamp` dev app, driven headless (offscreen) by logos-qt-mcp: **2/2 green** — the view instantiates and renders (no `std::bad_alloc` — the `exo-c6a` crash is gone), and `muster_module.health()` marshals back to `"ok"` (the `exo-526` concern, clean on the coherent chain). The muster-repo change is just `ui/flake.nix`.

  **Context.** `muster-ui.lgx` is already a C++/QtRO `ui_qml` module (a `.rep` replica + a C++ backend, `interface: universal`) — the *same architecture* as `demo/muster-ui`. It does not render to acceptance only because [`ui/flake.nix`](../ui/flake.nix) sets `logos-module-builder.follows = "muster_module/logos-module-builder"` — i.e. it is built by the **Nim-cdylib-authoring branch** of the builder, whose QML view-glue codegen targets `logos-cpp-sdk e3744fb8` / `logos-view-module-runtime 3c3735c2`. basecamp's ui-host runs `4b66dac0` / `1fde7d43`, so the view instantiates into `std::bad_alloc` (`exo-c6a`). Overriding just the input revs does **not** help: the branch's codegen still *emits* `e3744fb8`-shaped glue. Crucially, the skew is confined to the UI view-glue toolchain — `qt-sdk c6be61d0` and `protocol 03842db5` **already match**, and basecamp already **loads and dispatches `muster_module`** (the Nim module is fine; only the UI view crashes).
- **ADR-014 Reuse the Status/Nimbus Nim stack** — **resolved (2026-08-23).** The wallet's Ethereum layer is built on the org's own Nim libraries rather than hand-rolled, because they are ours to reuse and battle-tested. The blocker was never willingness — the shipping `logos-module-builder` compiled the module's Nim **stdlib-only** (linking C libraries, but pulling no Nim packages), which is why the P0–P2 crypto was thin FFI to C libs. Resolution: add a **`nim.packages` hook** to the builder (a pinned `{owner, repo, rev, hash, subdir?, submodules?}` list fetched from GitHub and added to the Nim `--path`) — the mechanism the builder's own comment anticipated. **Reused:** `stint` (amount arithmetic — `UInt256` is the EVM word, replacing a hand bignum); `nim-secp256k1` (one secp source — `crypto/secp256k1.nim` rewritten onto it, the hand FFI **and** the system `libsecp256k1` link dropped, so it no longer collides with nim-eth's own secp); `nim-eth` (EIP-155 RLP tx signing, and `verifyMptProof` — the Nimbus verified-proxy core — for verified reads, see mech-verified-reads); `nim-web3` (typed `eth_*` RPC over chronos, replacing hand-built JSON-RPC); `nimcrypto`. **Kept ours, deliberately:** `dcbor` (invariant 5 — deterministic signing-path encoding is ours to enforce, the platform's is non-canonical) and `curve25519`/libsodium (the F-14 chat-curve identity). **Costs accepted:** chronos is now the module's async runtime (first use; consistent with the chronos-only agreement — driven synchronously via `waitFor` at the sync lidl boundary); `nim-bearssl` vendors BearSSL C via a git submodule, so the builder hook gained per-package `fetchSubmodules`. **Verified behavior-preserving:** the full crypto/coordination suite and **all 42 invariant probes** pass on nim-secp256k1 with no system lib; `safe_anvil_e2e` runs green on live anvil (on-chain proof the secp migration is valid, not just unit-valid); the EIP-155 signing matches the canonical vector byte-for-byte; the verified-read primitive is tested self-contained. The builder's `nim.packages` hook + `fetchSubmodules` are local fork commits (branch `nim-cdylib-authoring`) worth upstreaming, alongside the ADR-013 RUNPATH fix.

  **Decision.** Build `muster-ui` with a **basecamp-coherent** `logos-module-builder` (mainline at basecamp's revs — `cpp-sdk 4b66dac0` + `view-runtime 1fde7d43` — **not** the Nim-cdylib-authoring branch), and stop following `muster_module`'s builder. `muster_module` keeps its own Nim-cdylib build and ships as a separate `.lgx` loaded into the same host; the two share the (already-matching) `protocol`/`qt-sdk` bus but no longer share the view-glue toolchain. This is precisely the pattern `demo/muster-ui` already ships: it follows `chat_module`'s coherent builder and still generates a typed client for a *different-repo* dependency it pulls in for its LIDL + runtime presence (`modules().lez_core.get_balance(...)`, `lez_core` from `logos-blockchain/logos-execution-zone-module`). The typed `modules().muster_module.<method>()` client is **kept** — the coherent builder generates it from `muster.lidl`, the same way the demo generates `lez_core`'s. `invokeRemoteMethod`-by-name is the fallback only if client-codegen against `muster_module`'s flake hits a snag.

  **Concrete change set (spec, not yet built):**
  1. `ui/flake.nix` — replace `logos-module-builder.follows = "muster_module/logos-module-builder"` with a pin at basecamp's coherent builder rev (or, proven-fastest, `follows = "chat_module/logos-module-builder"` with a `chat_module` input sourced only for that builder, mirroring the demo). Keep `muster_module.url = path:../module` as an input **only** so its `muster.lidl`/metadata is available for client-codegen and it lands in the runtime module set — its packages are built by its own flake, not this builder.
  2. `ui/metadata.json` — unchanged in shape (`type: ui_qml`, `interface: universal`, `codegen.rep`, `dependencies: ["muster_module"]`). Add any runtime `nix.packages` the coherent host needs (the demo carries `qt6.qtdeclarative`, `zstd`, `krb5`, `abseil-cpp`).
  3. `ui/src/*` — no rewrite. The backend keeps calling `modules().muster_module.health()/describe()/propose()`; only the toolchain that compiles the generated client + view-glue changes.

  **Risks / what a spike must confirm before committing:** (a) that a coherent (non-cdylib) builder will generate the `muster_module` typed client from its LIDL when the module was built by a *different* builder — the demo's `lez_core` says yes, but `muster_module` is Nim-behind-cdylib, not Rust/C++, so verify the flake exposes what client-codegen reads; (b) that `muster_module`'s string returns marshal correctly to this client over the bus — the typed path was the verified-good one for `exo-526`, but confirm on the coherent chain (`health() → "ok"`, `describe() → JSON`, `propose() → id`); (c) the `libsecp256k1` RUNPATH fix still applies to the module's `.lgx` in this host ($ORIGIN drop or `-rpath`). **Acceptance:** `muster-ui` renders in basecamp under `xvfb-run` + `QT_QUICK_BACKEND=software`, the health probe shows `muster_module.health() → ok`, and `propose` drives the re-materialization strip (effect → real re-derived `safeTxHash`) — the same logos-qt-mcp flow `exo-c6a` targets, reached by the coherent chain instead of the upstream fix.

  **Cost.** A second builder pin in the tree (UI coherent, module cdylib) until `exo-c6a` lands; a small divergence from ADR-008's "one shared chain" intent, explicitly time-boxed. Gain: the real invariant-backed lifecycle becomes visible in a UI now, and the P4 acceptance test (ADR-012 claims registry, the six-step legend) can be built against a running surface rather than waiting on upstream.

  **Spike result (2026-08-21, `exo-193`) — mechanism VALIDATED, two corrections.** A source trace of `logos-module-builder` (`buildCppPlugin.nix`, `mkLogosModule.nix`) confirms the load-bearing assumptions: (1) the typed `modules().muster_module.*` client is generated and compiled **by the consuming UI module's builder**, from `muster_module`'s published `.lidl` output (`packages.<sys>.lidl`) — for a `cdylib` module that output is a straight copy of the committed `muster.lidl`, so the module is **read, never rebuilt** (`mkLogosModule.nix:762-795`); (2) the client **and** the QtRO view-glue compile against the **UI builder's own** `logos-cpp-sdk`/`logos-qt-sdk`/`logos-protocol` pins (`buildCppPlugin.nix:111-131`, `:207-218`). So building `muster-ui` under a basecamp-coherent builder makes its view-glue ABI-match basecamp's ui-host, while `muster_module` keeps its Nim-cdylib build untouched — exactly ADR-013's bet.

  Two corrections to the framing above: **(a)** `logos-view-module-runtime` is **not** a compile input to the plugin at all — it is threaded only into `logos-standalone-app` (the runtime host side). The compile-relevant roots are `cpp-sdk`/`qt-sdk`/`protocol`; the fix is "build the UI under basecamp's builder," not "pin view-runtime." **(b)** The specific SDK revs cited above (`e3744fb8`, `4b66dac0`, `1fde7d43`, `c6be61d0`, `03842db5`) are **stale** — a lock cross-check on 2026-08-21 shows basecamp has rolled forward (its recorded `view-runtime 1fde7d43` is gone from every current lock; basecamp now pins builder `4717b9af`). Treat those revs as illustrative of *a* skew, not *the* skew. The durable action is rev-independent: **set `ui/flake.nix` `logos-module-builder.follows`/pin to basecamp's current builder (`4717b9af`)**, then verify by build + render. One precondition to keep true: `muster_module` must publish its `lidl` output (it does — `interface: cdylib` + `codegen.lidl`); if it ever stops, the consumer falls back to a transitional header path that *does* rebuild the dep and re-couples the chain (`common.nix:141-213`). Remaining unknowns are runtime-only and need the actual build: bus string-marshalling on the coherent chain (`exo-526`) and the `libsecp256k1` RUNPATH.

## Working agreements for Claude Code

- Re-validate the stack decisions table against current upstream HEADs at the start of every phase. The platform moves faster than this document; a stale assumption found at P0 is cheap, the same one found at P4 is not.
- poc2 and the LOGOS-MODULE-* specs are reading material, not build targets (ADR-008). Where they diverge from each other the spec is the better read; where either diverges from what `logoscore` actually loads, the shipping host wins.
- Conformance before features: the suite (S-1) is written first and extended with every driver capability; no driver work merges red.
- Integration tests never mock `Driver` or `Transport` — use the stub driver and the local transport instead. Mocks hide exactly the seams this architecture exists to expose.
