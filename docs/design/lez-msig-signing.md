# lez-msig: what a signer signs

*For integrators who use the lez-msig program without Muster: a custodian's HSM or MPC, a
hardware wallet, or another coordination client. This is the "signing seam" of the RFP-005
roadmap (`docs/proposals/RFP-005-roadmap.md` §1.1, milestone M2). The program is the only
authority. How approvals travel between signers is yours to choose.*

The source of truth is the program's own core: `programs/lez-msig/core/src/types.rs` (what is
signed) and `digest.rs` (how it is hashed). Test vectors, generated by that code, are in
`module/tests/vectors/lez-msig/vectors.json` (§6). If this page and the code disagree, the code
wins. Please file the disagreement.

## 1. Primitives

- **Signatures** are BIP-340 Schnorr over secp256k1. A member's key is the 32-byte x-only
  public key. The program verifies with `k256`'s `verify_raw`, which takes the 32-byte message
  as given and does not hash it again.
- **Tagged hash** is BIP-340's: `tagged(tag, m) = SHA256(SHA256(tag) ‖ SHA256(tag) ‖ m)`.
  Tags are ASCII.
- **Encoding** is borsh:
  - integers are little-endian at their stated width;
  - `Vec<T>` is a `u32` count, then the items;
  - fixed arrays (`[u8; 32]`, `[u8; 64]`) are raw bytes;
  - `bool` and `Option` are one byte (`0` or `1`, then the value for `Some`);
  - an enum is a `u8` variant index, then that variant's fields in order.

  The program decodes only exact bytes: no trailing byte, no non-canonical bool.

Every message commits to the multisig's account, its zone, its configuration epoch, a nonce and
an expiry. So a signature is worthless for any other multisig, any other zone, after any config
change, more than once, or after it expires.

## 2. The types that are signed

`Key` is `[u8; 32]`. Variant indexes are in brackets.

```
Proposal { multisig: Key, zone: Key, epoch: u64, nonce: u64, action: Action, expires_ms: u64, proposer: Key }

Action
  [0] Transfer { to: Key, amount: u128 }                        native LEZ out of the vault
  [1] Call     { program: Key, rows: Vec<Row>, data: Vec<u8> }  Row { account: Key, program: Key }
  [2] Config   (Vec<ConfigChange>)
  [3] Cancel   (Vec<u64>)                                       nonces to unqueue and spend

ConfigChange
  [0] AddMember(Member)            Member { key: Key, roles: u8, weight: u16 }
  [1] RemoveMember(Key)
  [2] SetRoles { key: Key, roles: u8 }        roles: PROPOSE 1 | APPROVE 2 | EXECUTE 4
  [3] SetWeight { key: Key, weight: u16 }
  [4] SetThreshold(u32)
  [5] SetTimelock(u64)                        milliseconds
  [6] SetOpenExecution(bool)
  [7] SetActions(u8)                          TRANSFER 1 | CALL 2
  [8] SetTargets(Vec<Key>)
  [9] AddLimit(SpendingLimit)      SpendingLimit { id: u32, signers: Vec<Key>, threshold: u8, amount: u128, period_ms: u64 }
  [10] RemoveLimit(u32)

Spend { multisig: Key, zone: Key, epoch: u64, limit: u32, nonce: u64, to: Key, amount: u128, expires_ms: u64 }
```

## 3. The four messages

| Who signs | Message (32 bytes) | When |
|---|---|---|
| each approver, and the proposer | `approve_msg = tagged("muster-msig/v1/approve", proposal_id)` | always |
| an EXECUTE member | `execute_msg = tagged("muster-msig/v1/execute", proposal_id)` | only if the config has `open_execution = false` |
| each of a limit's signers | `spend_msg = tagged("muster-msig/v1/spend", borsh(Spend))` | a spend under a spending limit |
| nobody | `proposal_id = tagged("muster-msig/v1/proposal", borsh(Proposal))` | the id the first two hash |

Show your signer the decoded `Proposal` or `Spend`, never `proposal_id` alone. The hash commits
to every field, but a person approving a hash approves nothing they can read. That gap is the one
behind Bybit and WazirX (RFP U.6).

## 4. Where each field comes from

Read the multisig's state from the chain first: its account's shard owned by the program,
borsh `State` in `types.rs`.

- `multisig`: the multisig's account id.
  - Public posture: the public PDA of (program, `tagged("muster-msig/v1/state", create_key)`).
  - Private posture: a group-owned private PDA. See §5.
- `zone`: `state.zone`, which the creator set at Create. Muster sets it to
  `tagged("muster-msig/v1/zone", <CAIP-2 chain id>)`, but any 32 bytes the creator chose are
  valid. Read it, don't recompute it.
- `epoch`: `state.epoch`. Every executed config change increments it, and every approval
  gathered before the change stops counting (R.2).
- `nonce`: any `n` with `state.nonce_base ≤ n < state.nonce_base + 256` whose bit in
  `state.consumed` is clear. Nonces can be used in any order, each once. Proposals and spends
  share the window.
- `expires_ms`: unix milliseconds. The program reads no clock. The transaction's validity
  window, enforced by the sequencer, keeps it from landing after this time.
- `proposer`: a member holding PROPOSE. Their `approve_msg` signature is required. It counts
  toward the threshold only if they also hold APPROVE.

## 5. Submitting

Any funded LEZ account can submit; the submitter gains no authority. The instruction is
borsh:

```
ProgramInstruction { create_key: Key, placement: Placement, op: Instruction }
Placement   [0] Public   (a private multisig's [1] Private { npk, vpk, identifier } is built by the prover)
Instruction [0] Create        { zone: Key, config: Config }
            [1] Execute       { proposal: Proposal, approvals: Vec<Signed>, executor: Option<Signed> }
            [2] Queue         { proposal, approvals, executor, at_ms: u64 }   with a time lock: at_ms is the latest landing time
            [3] ExecuteQueued { proposal, executor, at_ms: u64 }              after the ETA: at_ms is the earliest landing time
            [4] Spend         { spend: Spend, approvals: Vec<Signed>, period: u64, period_ms: u64 }
Signed      { key: Key, sig: [u8; 64] }
```

It goes in a LEZ v0.3 public transaction to the program. The transaction's rows are the
multisig's own shard, then what the action moves:
- for a transfer or a spend, the vault's native shard and the payee's;
- for a call, its rows.

Muster's Nim client builds this transaction (`module/src/wallet/lez_msig_chain.nim`,
`msigShards`), and so does the Rust host (`programs/lez-msig/host`).

The program refuses with a stable error code first in its message (`core/src/error.rs`), and on
v0.3 a refused transaction is still included. **Judge the outcome by the state you read back:**
the nonce is consumed, or the proposal is queued. Inclusion alone tells you nothing.

The **private posture** needs the group secret to prove a transaction. A signer who only holds a
key cannot submit there. Its approvals count the same, and a member holding the secret proves
the transaction (`lez_msig_module`). An integrator whose keys live in an MPC system will usually
run the public posture.

## 6. Test vectors

`module/tests/vectors/lez-msig/vectors.json`, generated by
`cargo run -p msig_host --bin msig_vectors`, with a fixed program, create key, zone and three
member keys:

| Key | What it is |
|---|---|
| `state_seed`, `multisig_public` | the PDA seed, and the public account it derives |
| `config`, `create_envelope` | a 2-of-3 config, and its Create instruction |
| `<kind>.proposal`, `.proposal_id`, `.approve_msg`, `.execute_msg` | for `transfer`, `call`, `config` and `cancel` |
| `<kind>.approve_sig1`, `.execute_sig3` | member 1's approval and member 3's execution, BIP-340 with a fixed aux |
| `<kind>.execute_envelope`, `.queue_envelope`, `.execute_queued_envelope` | the instructions that carry them |
| `spend`, `spend_msg`, `spend_sig1`, `spend_envelope` | a spend under limit 7 |
| `state` | a multisig's state shard, as `readMsig` decodes it |
| `aux` | the BIP-340 auxiliary randomness the signatures above use |

Muster's Nim port reproduces every one byte for byte (`module/tests/lez_msig_bytes_test.nim`).
An integrator's implementation should do the same before it signs anything real.

## 7. What the program checks at execution

These are R.1 and R.2, in `core/src/rules.rs`:
- the account, zone and epoch match the state;
- the nonce is free;
- the action kind and target are allowed;
- the approvals come from distinct current members holding APPROVE, each a valid signature over
  `approve_msg`, and their weights sum to at least the threshold;
- the proposer signed;
- the executor signed, when execution is closed;
- the time lock is honoured, when the multisig has one.

A spend instead needs its limit's threshold of the limit's own signers, the current period, and
room left under the limit's amount for that period.

## 8. Signature schemes

Today every key is BIP-340. Custodial MPC stacks commonly sign Ed25519 and ECDSA secp256k1, but
not BIP-340 (see the roadmap, §4.3). Accepting Ed25519 member keys alongside BIP-340 is tracked
as exo-0d3.20. It would add a scheme byte per member, and with it a new version of these
messages.
