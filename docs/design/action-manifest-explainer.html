The credibility axis is a matrix, not a score

The PriFi article splits commitments into imperative (the discretion to defect is removed structurally) and motivational (the party could defect but has a reason not to). Muster's data forced two more values: exposed, where no binding exists because information reaches an unbound observer, and not applicable. The unit is a lifecycle step crossed with an observer. The submit cell against the RPC provider is the article's private-order-flow example exactly: the user-configured endpoint sees the signed transaction before the mempool does. Muster relocated that discretion, it did not remove it, and the registry now says so with a named party.

A proof of the log refuses on any tamper

  
Every event is content-addressed: its id is the digest of its parents, key, and value. A proof is the canonical slice plus the claimed ids, parent-closed, reaching a state digest. Edit any value below and the recomputed id stops matching; the verifier names the first discrepancy. This demo hashes with SHA-256 over a simplified record. The real record is a domain-separated dCBOR hash-input, but the property is the same.

Where the host comes in

  
Today the host's policy answers who may call whom. Muster answers what was agreed. M7 is the seam between them. The muster side exists: a grant issued only for an executable intent, replay-bound and signed, with a pure checker. The upstream side is where the draft specs changed the shape of the ask.

  
  

    
A · Bespoke hook (interim)
  • Policy names an authorization format and trusted issuers, never a module.
  • Broker recomputes the call's root and compares to the grant's. Argument-level prevention, today.
  • Cost: the broker carries muster's encoder, or asks muster, which puts muster on the dispatch path.
  • Nothing changes for an unlisted capability.

    
B · Capability Authority, slug 312
  • Runtime obtains an allow decision per call naming the one method checked. Grants are policy state: contract, method, route, expiry, revocation.
  • Muster calls issue_grant when a room folds to executable. Zero muster-specific enforcement code; caching, revocation, audit for free.
  • Scopes cannot bind args: request roots "normally do not exist when an allow decision is made". Binding lands in audit via retain-root.
  • Ask: an optional expected request value root on provider_access_scope.

What the platform draft says, and what is ratified

  
Checked at logos-co/logos-lips branch draft/logos-core-module-specs, head e50463f of 2026-09-13, on open PR #317. Every LOGOS-MODULE-* spec on it is Status: raw. Four findings, and a hash-suite gap that is easy to miss.

  
  
Status board

  

  

  
The four questions to ask

  
1. Is Basecamp implementing LOGOS-MODULE-CAPABILITY-AUTHORITY, and when? If yes, the ask is policy that lets muster_module issue grants narrowed to a method, route, and expiry. If no, path A is the fallback.

  
2. Would the editors accept an optional expected request value root on provider_access_scope, so enforcement can refuse a call whose args differ from what was agreed rather than only retaining the root for audit?

  
3. Who is the issuer of record for a room's grant: the muster instance, named, or for anonymous rooms a threshold signature the room produces? The spec's consumer is an authenticated instance address either way, so anonymity has to live in the room, not the grant.

  
4. Hash-suite timeline. Commitments are BLAKE3-256 under the draft; muster signs under SHA-256 and keccak. When the profile ratifies, muster implements it and grant roots become the platform's call roots.
